# 建房设计、施工找人与工程报价平台

日期：2026 年 11 月 3 日

状态：已合并本轮讨论中的产品取舍；地区、技术供应商与合规事项仍待确定。

适用范围：产品规划、UI/UX 设计与首版开发拆分。

## 1. 本版结论

Yusal 帮助业主把建房想法或已有设计变成清楚的施工需求，找到工人和施工队，获得可比较的报价并确认合作。

首版核心场景：业主无需画图也能发布砌墙需求；已有设计时自动带出工程量；当地施工队提交范围清楚的报价；双方确认合作；平台能够了解最终是否找到人。

产品有两个相互连接的入口：

- 直接找人：填写施工或招工需求，不要求先使用设计工具。
- 从设计找人：打开设计，选择整栋或施工阶段，生成附带图纸和工程量的需求。

设计工具继续支持独立使用。查看公开信息、试用设计和粗估费用不强制登录；发布、报名、报价、联系及云备份时再登录。

## 2. 产品定位与边界

首发面向哈萨克斯坦私人建房、翻新和分项施工，优先集中一个城市及周边地区。首发语言为哈萨克语、俄语，保留中文。

核心差异是“设计版本 + 工程量 + 承接范围 + 报价”，让双方讨论同一项工程。首版不承诺施工质量、付款保障或官方审图能力。

### 用户与任务

| 用户 | 首要任务 | 核心入口 |
| --- | --- | --- |
| 业主 | 估算费用、发布需求、比较施工方 | 找人、我的项目 |
| 工人 | 找到附近合适的活、明确工资和到岗时间 | 找活、个人名片 |
| 包工头／施工队 | 找项目、提交报价、补充招人 | 找活、团队名片、发布需求 |

一个账号可同时发布需求和接活。注册不强制固定身份；用户按需创建个人或团队服务档案。企业独立账户、队员权限与派工管理后补。

### 不进入首版的范围

建材电商、材料商导流、内容社区、短视频、关注关系、复杂推荐、地图找活、语音聊天、资金托管、保险贷款、共同编辑、企业组织管理、技能等级体系。

## 5. 需求模型：两个类型，一个发布入口

原来的四种帖子收敛为两种需求。整栋承包、分项、转包、分包作为范围或来源属性，不单独建立四套发布与状态流程。

| 类型 | 示例 | 对方动作 |
| --- | --- | --- |
| 招人干活 | 找两名瓦工，按天结算 | 报名，说明到岗时间与期望工资 |
| 找人承包 | 130 平米住宅砌墙 | 报价，说明承接范围、价格与工期 |

### 5.1 公共字段

必填：需求类型、工作内容／工种、地区、预计时间（可选待协商）、联系与通知所需账号信息。标题可以由字段生成并允许修改。

可选：文字说明、照片、预算、设计关联、具体地址、现场限制。公开只展示城市／村镇／街区；精确地址由发布者单独向合作方授权。

预算支持区间、明确金额、“不确定，请报价”；不能用填写虚假数字的方式通过校验。价格单位与人工／材料范围必须分开表达。

### 5.2 招人干活字段

人数、日薪／计件／其他计酬方式、已知工资或面议、预计工作天数／日期、是否提供食宿、工具由谁提供、结算周期。日期、工资待协商时明确标记。

报名填写可到岗时间、期望工资（与原条件一致可直接确认）、补充说明。团队报名可填写可提供人数；最终录用人数由双方明确确认。

### 5.3 找人承包字段

承接范围（整栋／施工阶段／自定义分项）、工程量与单位（未知可注明现场测量）、人工／包工包料要求、预计开工时间、目标工期、预算方式、报价截止日期。

分包需求另标注发布者身份及其与项目的关系；不自动把发布者当作房屋所有人。

## 6. 工人和施工队名片

必需信息：姓名或团队名称、工种、服务地区、个人／团队、接活状态。经验、参考价格、人数和作品可逐步完善，不要求写正式简历。

接活状态：现在可接、指定日期后可接、暂不接活。显示最近确认时间，长时间未更新时提醒本人确认；找人列表可筛选当前可接者。

参考价格必须带单位和适用范围，例如“仅人工，砌墙每立方米起”；最终以具体报价为准。

作品分为自主上传和关联平台合作记录，清楚区分来源。合作结束后经授权关联项目图片，不能自动公开业主图纸或地址。

首版只展示可证实的信息，例如手机号已验证、经双方确认的合作次数、有效评价数。资料不足不展示虚构星级；暂不展示按时率和模糊的“平台担保”标识。

## 7. 设计到施工需求

### 7.1 两条发布路径

直接发布：选择招人／承包 → 填写需求 → 添加照片或图纸 → 预览 → 发布。

从设计发布：打开项目 → 找施工方 → 选择整栋或基础、墙体、屋顶、水电暖等阶段 → 自动提取相关工程量 → 用户确认范围和公开附件 → 补充地区、时间和预算 → 发布。

工程量提取失败或不适用时，允许手填并标明来源。设计检查结果不等于具备施工或审批资格，不能阻断所有普通询价。

### 7.2 发布快照

发布时保存设计版本、提取时间、范围、工程量、单位和选定图纸。原设计后续变化不覆盖已发布附件。

| 变化 | 处理方式 |
| --- | --- |
| 尚无人报价 | 可发布新的需求版本，保留修订记录 |
| 已有人报价 | 通知报价方范围变化，原报价标记待重新确认 |
| 已确认合作 | 新版本作为变更提案，双方确认后生效 |

不允许将旧报价无提示地套用到新工程量。

### 7.3 附件隐私

用户分别选择是否公开工程量、平面图和效果图。完整 .house 文件、精确位置、家庭备注默认不公开。分享链接只展示获准公开的版本，可撤销；首版支持帖子网页与选定图纸，交互 3D 网页后补。

## 8. 报价与对比规则

承包报价至少包含：报价所依据的需求版本、承接范围、仅人工／包工包料、按量／总价／现场确认、工程量与单位、单价或总价、预计工期、不包含项目、有效期。运输、设备、清运、税费等可在包含／不包含清单中说明。

按量报价自动计算数量乘单价；总价报价说明覆盖范围。“需现场确认”作为明确报价状态，不能与确定总价混排而不提示。报价方无法确认某项时可先请求补充资料。

首版提供简单的并排或纵向对照，不做最低价推荐。不同材料范围、单位或设计版本的报价提示不可直接比较；报价列表显示价格、范围、工期与待确认项。

每个服务档案在同一需求下保留一份当前有效报价，允许修改并保留历史；已确认合作后的修改走变更确认。

## 9. 分开的业务状态

### 9.1 需求状态

| 状态 | 含义 |
| --- | --- |
| 草稿 | 仅本人可见 |
| 待审核 | 已提交，等待审核 |
| 招募中 | 可报名／报价 |
| 暂停 | 暂不收新申请，已有沟通和合作保留 |
| 已找到人 | 停止新申请，可记录平台内或平台外结果 |
| 已到期 | 截止或有效期结束，可续期 |
| 已关闭 | 发布者结束需求，记录原因 |
| 审核未通过／下架 | 展示原因，允许按规则修改或申诉 |

录用一人不自动关闭需求。发布者可以继续招人，也可以标记已找到人。到期只影响新申请，不取消既有合作。

### 9.2 报名／报价状态

已提交、已撤回、未选用、待对方确认、已形成合作。已读、是否沟通作为辅助信息，不作为严格业务阶段。

发布者撤销邀请或申请人拒绝时，不能直接形成合作；确认超时可重发邀请。重复点击提交应避免创建重复申请。

### 9.3 合作状态

待双方确认 → 已确认合作 → 已结束。施工进度更新可选；取消／争议作为独立结束原因或处理标记，保留记录。

合作约定包含：双方、工作范围、设计／需求版本、录用人数或承包内容、金额和计价方式、预计时间、付款节点、材料工具责任、待确认事项。界面称“合作约定”，首版不直接宣称为具有特定法律效力的电子合同。

双方分别确认，同一账号不能代替对方确认。修改范围、金额、付款条件时产生新约定版本，原版本继续可查；只有双方接受后新版本生效。

一方发起结束，另一方可确认或提出异议。无人回应时标记“单方报告结束”，不能冒充双方验收。评价不是结束的必需步骤。

## 10. 联系、消息和分享

首版聊天支持文字、图片、需求卡片和报价卡片。建立会话须登录；聊天须具备拉黑、举报、发送频率限制与发送失败重试。语音和视频后补。

手机号默认隐藏。用户可主动向指定对方展示电话，或选择联系 WhatsApp；需要清楚说明会向外部应用暴露哪些联系方式。平台不以跳转外部应用作为成交证据。

系统通知覆盖新报名／报价、确认请求、约定变更、结束请求、评价、需求到期和结果回访。通知点击进入对应业务对象；已关闭、下架或无权限对象显示明确状态。

使用系统分享面板发送帖子卡片和链接，可分享到支持的外部应用；不承诺每个社交应用都支持相同的一键发布形式。未安装应用可先在网页查看公开详情，再登录报名／报价。

## 11. 结果回访、评价与信任

### 11.1 轻量结果回访

建议在发布后第 3 天及到期时询问，时间可配置：是否找到人、是否通过 Yusal 找到、是否需要继续招募。已关闭或已回答用户不重复打扰。

结果区分：平台双方确认合作、发布者自报通过 Yusal 联系成功、通过其他渠道找到、尚未找到、暂不需要。自报成交不能计入双方确认合作数，也不能直接生成“已验证完工”作品。

### 11.2 评价

双方确认结束的合作开放双方评价，评价可跳过。自报结果与未完成核实的纠纷不伪装成已验证评价。按时付款、范围清晰、沟通、施工体验等采用少量明确维度；评分汇总方式在界面规则中公开。

评价窗口结束或双方提交后再互相公开，降低报复性评价压力。举报不等于事实成立，公开欠薪等争议信息需有审核与申诉机制。

### 11.3 基础安全

手机号验证、新用户内容审核、举报、拉黑、重复信息与垃圾消息限制必须进入首版。提示工人不要缴纳招工押金。平台没有托管服务时，不能展示付款保障文案。

首版不把收集 ИИН、人脸作为默认注册步骤。完整实名认证的必要性、供应商、数据保存和隐私责任确定后另行上线；手机号验证不称为实名。

## 12. 估价与本地项目备份

### 12.1 估价

保留现有设计预算：工程量乘单价，显示地区、币种、单价来源和更新时间；示例数据明确标注示例，允许修改。只对具备依据的范围给出估价，说明不包含项。

无需画图的快速估价分两步实施：首版准备入口与参数结构；有本地样本、估价口径与维护责任后开放。无法校准时不以“30 秒准确知道造价”推广，不用随意扩大区间掩盖缺少依据。

地区材料单价、人工报价与完整工程总价分开存储。成交数据只在用户同意、数量足够且口径可比时用于匿名统计，不能把少量不同范围的报价简单平均成市场价。

### 12.2 备份而非实时共同编辑

本地保存和自动保存继续有效。登录后用户可备份项目、查看备份时间、在另一设备恢复。自动备份可在手动流程可靠后增加；首版不承诺实时多端同步。

本地与云端都变化时，显示两个版本及时间，支持保留副本或由用户选择；不能静默覆盖。上传失败不影响本地编辑，展示待重试状态。恢复不支持的文件版本时说明原因，不写坏原文件。

版本历史、完整同步、共同编辑后补。公开需求快照与个人项目备份分开授权，撤销公开分享不删除个人备份。

| v1.2 | 增加工人重复使用价值 | 记工记账、对账单、报价 PDF、可选施工照片、经合规评估的身份核验 |
| v2 | 验证付费价值 | 团队管理、专业版、标记推广；托管仅在合规与合作机构落实后单独立项 |
| 后续 | 扩地区与服务 | 技能证明、保险与专业服务、共同编辑、中亚其他地区 |

首版内部按依赖拆分交付：账号与名片 → 直接发需求与报名报价 → 联系与合作 → 设计快照接入 → 备份、运营和发布验收。可以分批内测，但不能将设计关联再次无限后移。

记工、报价单等基础工具坚持工人免费；完整管队能力不承诺永久免费，与未来团队专业版范围区分。

## 14. 管理后台与运营

最低后台能力：需求和名片审核、违规下架、举报和申诉处理、账号限制、工种／地区维护、到期策略、基础指标查询。审核操作保存操作人、时间、原因，方便追溯。

冷启动集中一个地区。邀请首批工人和施工队，帮助完善名片并确认接活状态；在发布者授权下代录真实需求，注明信息来源并让发布者认领。不得未经许可抓取联系人或冒充用户。

先访谈并陪跑业主、工人和包工头，重点观察：他们怎样描述范围、用什么单位报价、为什么需要看现场、什么时候愿意确认合作。发布量之外，人工核对是否真的联系上和是否接到活。

## 15. 指标与验收

### 15.1 关键指标

| 指标 | 定义／用途 |
| --- | --- |
| 有效需求 | 审核通过、未失效且信息可联系的需求 |
| 首次有效响应时间 | 发布到首次真实报名／有效报价的时间，排除垃圾回复 |
| 响应覆盖率 | 观察期内至少收到一次有效响应的需求占比，按类型分开 |
| 确认合作率 | 固定发布批次中，至少形成一份双方确认合作的需求占比 |
| 自报匹配结果 | 与双方确认合作单独统计，用于发现外部联系成果 |
| 报价可比较率 | 范围、版本与计价单位明确的承包报价占比 |
| 设计关联使用率 | 附带有效设计快照的承包需求占比及其响应情况 |
| 供给活跃 | 活跃接活名片、有效响应人数、工人周留存 |
| 安全与处理质量 | 举报类型、核实违规数、处理时长、申诉情况；举报率低不直接等于安全 |

暂不设虚构目标数；内测获得基线后按地区和类型设目标。新发布需求不能与已有完整观察期的需求混在同一转化率分母中。

### 15.2 MVP 验收场景

1. 未登录用户能浏览公开需求与名片，登录后继续刚才的报名或发布操作。
2. 无设计的业主可发布招人或承包需求，预算未知也能提交完整有效信息。
3. 有设计的业主可选施工阶段，确认工程量与公开图纸，并生成固定版本附件。
4. 工人能报名并说明到岗时间；施工队能提交范围明确的报价，双方可沟通。
5. 发布者能对比报价；单位、材料范围或版本不一致时有明确提示。
6. 一个需求可录用多人，已找到部分人时仍能继续招募。
7. 合作必须双方确认；变更须重新确认，原约定可追溯。
8. 设计修改不会静默修改已发布工程量和已确认报价。
9. 合作可结束而不评价；单方报告不显示为双方验收。
10. 需求到期后停止收新申请，已有合作仍能访问；发布者可续期或关闭。
11. 默认公开页面不泄露电话、精确地址、完整文件和家庭备注。
12. 外部分享网页可查看允许公开的信息；撤销或下架后页面正确提示。
13. 离线可编辑本地设计；备份失败不丢数据，冲突不静默覆盖。
14. 用户可举报和拉黑；后台可处理并记录原因；哈俄中核心流程文案齐全。

## 16. 技术实施原则

保留现有 pure Dart 设计计算核心、文件兼容、渲染和存储边界。新增账号、需求、名片、报价、合作、消息、审核模块；不要把平台订单数据塞进 .house 设计文件。

设计文件、发布快照、需求版本、报价版本、合作约定分别具有稳定标识。账号身份与个人／团队服务档案分开，保留未来团队权限空间，首版不实现完整组织管理。

后端负责权限、状态转换、双方确认与审计，客户端不能直接把自己改成“已录用／已验证”。考虑重复提交、断网重试、并发修改和图片上传失败。聊天与业务记录应互相关联，但聊天文字不能代替明确确认操作。

Firebase 与自建服务尚未选定；现有 Hosting 配置不作为后端选型理由。选型需一起评估团队维护能力、短信成本、文件流量、查询需求、数据所在地和供应商能力。本版不对哈萨克斯坦法律要求作结论，发布前由本地专业人士核验个人数据、用工撮合、协议与投诉责任。

## 17. 商业模式

工人基础找活、报名和接单免费，不按线索收费。MVP 免费验证真实匹配；不预设托管费率。

后续候选收入：团队多项目管理与协作订阅、清楚标识的付费推广、具有独立价值的专业服务。认证只表达核验事实，不能把购买订阅直接等同于实名或施工质量认证。
